Haiku 4.5 vs Opus 5: what the numbers actually say

Seven dispatch strategies over the same 36-task workload, run three times end to end, every call charged to the strategy that made it. Running it repeatedly is the point: the spread between identical runs is the noise floor, and no conclusion may rest below it.

What the seven strategies are

Two of these rows are baselines. The rest are attempts to land inside the gap between them — and there are only two ways to try: guess before you generate, or check after.

The column that tells the story is Sent to Opus. All three guess-before routers land at 58–67%: when unsure, they panic and pay up, which is why none saves more than a third. The cascade sends 14% — not because it guesses better, but because it does not guess at all.

The trap is the obvious design. “Ask a smart model which model to use” comes last on every axis: dearest of the routers, slowest at 3,685 ms, and 18.1% of its budget spent deciding rather than answering.

Why did the cascade top the accuracy column?

It shouldn't have, and running the benchmark twice more settled it: it doesn't. The cascade topped the table once in three runs. A strategy sending 86% of traffic to the cheap model has no business out-scoring the expensive one, and across identical reruns it didn't.

The accuracy winner changed in all three runs — heuristic + cascade, then oracle, then heuristic + oracle. Meanwhile the cost ordering was identical every time. That contrast is the entire methodological point of this page.

One task tells the whole story. In run 1 the cascade escalated h11 to Opus and got it right, while always-Opus asked the same model the same question and got it wrong. Then it flipped again in run 2. Sixteen such per-task flips occurred between runs 1 and 2 alone. If a model disagrees with itself, a 36-task suite cannot rank strategies that differ by two tasks.

What survived all three runs: the cascade never lost accuracy against always-Opus, and cut cost by roughly half every time. That is the claim. “More accurate” was never one.

Performance

Latency is the axis dispatch usually makes worse. The cascade pays for an extra round trip on every request; the LLM classifier pays for two.

The cascade lands at 2,735 ms — essentially always-Opus latency (2,769 ms) for 41% of always-Opus cost. It buys the saving with round trips, not with a faster model. The classifier is the worst of both: slowest and second-most expensive.

If time-to-first-token matters, cascade is the wrong tool. It cannot stream — the verifier needs the complete cheap answer before it can judge, so a streamed cascade would buffer the whole response. Streaming traffic falls back to the zero-token heuristic, which decides before any tokens are generated.

Tripling the data changed one conclusion and confirmed another. “Is Opus better than Haiku?” went from unresolvable (p=0.453) to yes (p=0.012) — so the earlier “not measurably better” was a statement about sample size, not about the models. But cascade vs always-Opus stayed dead even at 5–4, p=1.000.

That combination is the finding: the cascade recovers always-Opus quality — indistinguishable across 108 paired instances — at 53% less cost, while being clearly better than always-Haiku (p=0.001). Not “better”. Equal, for half the money.

An escalation costs 18× a clean cascade hit and takes ~1.7× as long. That ratio is why the escalation rate — 14% here, against a true need of 14% — is the number to watch in production, not the average.

And the lever that beat all of this. Driving the same Claude backend from Codex CLI, whose harness resends a 13,443-token prompt every turn: caching that prefix took the steady-state turn from $0.069 to $0.0155 — 78% off, no model change, no quality risk. The router sent every one of those requests to Opus anyway, because a 13k prompt trips every length signal there is.

Ranked by what the numbers support: fix caching first (78%, no quality risk, measured). Then cascade dispatch (59%, no detected regression, +100% latency). Do not build the LLM classifier (17.5%, slowest, 18% of its budget spent deciding).

Dynamic selection inside Codex and Claude Code

The proxy above translates between providers, and that is what stops a coding agent: Codex's tool calls cannot cross into Claude's format, and claude -p never returns a tool call at all. Pass-through mode stays inside one model family. It picks the cheap or the expensive model of the same family, rewrites only the model field, and forwards everything else unchanged — tools, tool results, streaming, the login — to the router the client already uses. No API key; tool calling works; the interactive Codex TUI works (Claude Code has so far been driven through claude -p).

codex-dmsCodex 0.156.1→ dms passthrough:8789 · picks luna or sol→ codex-router:18790 · ChatGPT login→ gpt-5.6-luna / gpt-5.6-sol
  • Only the main model is ever changed. Anything else the client asks for — a safety classifier, a background call — passes untouched.
  • Each typed message is scored. The zero-token heuristic reads what you typed, not the context the client wraps around it.
  • Tool steps keep their turn's model — unless the conversation outgrows the cheap model's context window, when it moves up mid-task. Otherwise switching would discard the prompt cache halfway through.
  • Every generation request is ledgered. Tier, tokens, status, latency — no prompt text, no credentials — in ~/.dms/usage.jsonl.

The bug this run found — fixed the same day. The proxy keeps a conversation off the cheap model once it outgrows that model's context window, and it estimated size as request bytes ÷ 3. The browser task's request had grown to 1 MB, 0.45 MB of it seven screenshots in base64: a 123k-token prompt read as ~340k — 85% of Luna's 400k window — so the rest of the turn went to Sol: $2.07, 63% of the day's spend, against $0.41 for the same tokens on Luna. Images now count as a fixed 2,500 tokens each, and the same request reads as ~207k.

Five live runs, and the one that lost money

“Saved” compares each run with sending every request to the model it asked for. Caches are per model, so that comparison has to give the expensive model the cache it would have kept warm — otherwise a switch's cold write shows up as a saving.

Why the last row lost money. Claude Code opens every session with the same ~52k-token prompt, and each model caches its own copy. The one message routed to Opus found Opus cold and paid a 66k-token write, $0.41. Had everything gone to Opus, that prefix would have been read from cache for $0.03, plus $0.09 for the rest. The cold write's extra $0.30 is more than the $0.11 the three Sonnet requests saved. This row was first reported as 16.3% saved; an adversarial review of the ledger found the comparison pricing that cold write as if Opus would have paid it anyway.

Routing down saves the whole price gap (40% for Sonnet under Opus) — but every model you route to needs its own warm cache, and on short Claude Code sessions that second cache costs more than the cheaper model saves. Codex pays less of it: most of its cache is per session, though new Codex sessions still opened with 2.8k–13k tokens already cached.

Chinese prompts no longer go to the cheap model by default

The heuristic's markers were English, and it measured length in space-separated words — so a Chinese message fired almost nothing and counted as only a few words: the old router sent just 13 of 81 hard Chinese messages high. It now reads Chinese renderings of every English marker and counts 1.5 Han characters as a word (the central estimate across FLORES, WMT and TICO-19 parallel text). English scores are pinned by a test and did not move.

Reviewed before it carried a login

The pass-through proxy holds the user's login header in memory on every request, so it went through an 11-agent review before it was pushed. Every finding of medium or high severity was reproduced, then fixed test-first.

Ranked by what the numbers support, updated: fix caching first (78%, no quality risk). For a coding agent, pass-through routing on one provider saved 16–56% across four live runs — but on short Claude Code sessions it lost 46% to a second cold cache, so measure it on your own sessions before trusting it. Watch what gets routed, not just the average: today's biggest cost was a proxy bug that sent a screenshot-heavy turn to the expensive model, found by reading the ledger and fixed the same day.
